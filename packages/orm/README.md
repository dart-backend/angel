## Usage

You'll need these dependencies in your `pubspec.yaml`:

```yaml
dependencies:
  angel3_orm: ^10.0.0
dev_dependencies:
  angel3_orm_generator: ^10.0.0
  build_runner: ^2.4.0
```

`package:angel3_orm_generator` includes a `build.yaml` that applies its builders, `ormBuilder` and `migrationBuilder`, to your package automatically, so you shouldn't have to do any configuration at all. Generate the code with:

```bash
dart run build_runner build
```

## Models

The ORM works best when used with `package:angel3_serialize`:

```dart
import 'package:angel3_migration/angel3_migration.dart';
import 'package:angel3_orm/angel3_orm.dart';
import 'package:angel3_serialize/angel3_serialize.dart';
import 'package:optional/optional.dart';

part 'car.g.dart';

@serializable
@orm
abstract class CarEntity extends Model {
  String get make;

  String get description;

  bool get familyFriendly;

  DateTime? get recalledAt;
}

// You can disable migration generation.
@Orm(generateMigrations: false)
abstract class NoMigrationsEntity extends Model {}
```

Models can use the `@SerializableField()` annotation; `package:angel3_orm` obeys it.

After building, you'll have access to a `Car` model and a `CarQuery` class with strongly-typed methods that
allow to run asynchronous queries without a headache. The generated classes are named without the `Entity` suffix.

Remember that if you don't need automatic id-and-date fields, you can
simply just not extend `Model`:

```dart
@serializable
@orm
abstract class ThisIsNotAnAngelModelEntity {
  @primaryKey
  String get username;
}
```

## Example

Routes that query the database:

```dart
import 'package:angel3_framework/angel3_framework.dart';
import 'package:angel3_orm/angel3_orm.dart';
import 'car.dart';

/// Returns an Angel plug-in that mounts routes for the `cars` table, queried with [executor].
AngelConfigurer carRoutes(QueryExecutor executor) {
  return (Angel app) async {
    app.get('/cars/recalled_since_2008', (req, res) async {
      // Instantiate a Car query, which is auto-generated. This class helps us build fluent queries easily.
      var query = CarQuery();
      query.where!
        ..familyFriendly.isFalse
        ..recalledAt.year.greaterThanOrEqualTo(2008);

      // `get()` returns a Future<List<Car>>.
      return await query.get(executor);
    });

    app.post('/cars', (req, res) async {
      // `package:angel3_orm` generates a strongly-typed `insert` function on the query class.
      // Say goodbye to typos!!!
      var query = CarQuery();
      query.values
        ..familyFriendly = true
        ..make = 'Honda';

      // `insert()` returns a Future<Optional<Car>>, auto-serialized using code generated by `package:angel3_serialize`.
      return (await query.insert(executor)).value;
    });
  };
}
```

Routes like these need no reflection. A `Controller` with `@Expose` methods needs an `Angel` created with a `reflector`.

## Relations

`angel3_orm` supports the following relationships:

- `@HasOne()` (one-to-one)
- `@HasMany()` (one-to-many)
- `@BelongsTo()` (one-to-one)
- `@ManyToMany()` (many-to-many, using a "pivot" table)

The annotations can be abbreviated with the default options (ex. `@hasOne`), or supplied
with custom parameters (ex. `@HasOne(foreignKey: 'foreign_id')`).

```dart
@serializable
@orm
abstract class AuthorEntity extends Model {
  @hasMany // Use the defaults, and auto-compute `foreignKey`
  List<BookEntity> get books;

  // Also supports parameters...
  @HasMany(localKey: 'id', foreignKey: 'author_id', cascadeOnDelete: true)
  List<ReviewEntity> get reviews;

  @SerializableField(alias: 'writing_utensil')
  @hasOne
  PenEntity? get pen;
}
```

The relationships will "just work" out-of-the-box, following any operation. For example, after fetching an `Author` from the database in the above example, the `books` field would be populated with a set of deserialized `Book` objects, also fetched from the database.

### Loading Relations

Relations are loaded with every query that returns records: `get`, `getOne`, `insert`, `update` and `delete`.

- `@HasOne()` and `@BelongsTo()` are joined, as each record is still one row.
- `@HasMany()` is loaded after the records, with one query for all of them (`WHERE author_id IN (...)`), rather than joined, which would return a row per item.
- `@ManyToMany()` is loaded with a query of the pivot table, then one of the other model.

The items loaded have their own relations loaded in turn, such as a `@HasMany()` of a `@HasMany()`, so the number of queries depends on the relations, not on the number of records. Fetching authors with their books and the books' reviews takes three queries, however many authors there are.

As a record is one row, `limit` and `offset` count records, and `getOne` fetches one row.

A relation back to a table that is being loaded is not loaded again, and is left empty: the `roles` of a `User` are loaded, but not the `users` of those roles, which would load the user again.

The query of a `@HasMany()` is the one its items are loaded with, so its conditions and order apply to them:

```dart
var query = AuthorQuery()..where!.name.equals('Jane');
query.books
  ..where!.published.isTrue
  ..orderBy('title');

// Jane, with only her published books, by title.
var author = await query.getOne(executor);
```

### Many to Many Relations

A many-to-many relationship can now be modeled like so. `RoleUser` in this case is a pivot table joining `User` and `Role`.

Note that in this case, the models must reference the entity classes (`UserEntity`, etc.), because the generated versions (`User`, etc.) do not exist yet:

```dart
@serializable
@orm
abstract class UserEntity extends Model {
  String get username;
  String get password;
  String get email;

  @ManyToMany(RoleUserEntity)
  List<RoleEntity> get roles;
}

@serializable
@orm
abstract class RoleUserEntity {
  @belongsTo
  RoleEntity get role;

  @belongsTo
  UserEntity get user;
}

@serializable
@orm
abstract class RoleEntity extends Model {
  String get name;

  @ManyToMany(RoleUserEntity)
  List<UserEntity> get users;
}
```

TLDR:

1. Make a pivot table, C, between two tables, table A and B
2. C should `@belongsTo` both A and B. C *should not* extend `Model`.
3. A should have a field: `@ManyToMany(CEntity) List<BEntity> get b;`
4. B should have a field: `@ManyToMany(CEntity) List<AEntity> get a;`

Test: <https://github.com/dart-backend/angel/blob/master/packages/orm/orm_postgres/test/many_to_many_test.dart>

## Columns

Use a `@Column()` annotation to change how a given field is handled within the ORM.

### Column Types

Using the `@Column()` annotation, it is possible to explicitly declare the data type of any given field:

```dart
@serializable
@orm
abstract class FooEntity extends Model {
  @Column(type: ColumnType.bigInt)
  int get bar;
}
```

### Indices

Columns can also have an `indexType`:

```dart
@serializable
@orm
abstract class FooEntity extends Model {
  @Column(indexType: IndexType.primaryKey)
  String get bar;
}
```

### Default Values

It is also possible to specify the default value of a field.
**Note that this only works with primitive objects.**

If a default value is supplied, the generated migration includes it in the schema; queries do not need it. A `String` default is a literal, which is quoted and escaped; for SQL, such as the current time, give a `RawSql` (e.g. `currentTimestamp`).

```dart
@serializable
@orm
abstract class FooEntity extends Model {
  @Column(defaultValue: 'baz')
  String get bar;
}
```
